Ralph Loop

Always-on autonomous multi-agent execution — design specification

Created: 2026-07-11  ·  Project: Axon  ·  Priority: HIGH  ·  Target: Aug 2026  ·  Status: DESIGN PHASE

01 The Core Idea

The Ralph Loop is an always-on autonomous execution architecture for Axon. Instead of waiting for user input to trigger actions, Axon agents run in a continuous loop, execute tasks autonomously, coordinate with each other via Telegram, and only surface to the user when a decision is required.

Two Axon instances already run simultaneously (ROG + Leonid). Both already communicate via Telegram. The Ralph Loop formalizes this into a structured multi-agent coordination system with shared goal context, inter-agent sync, and a meta-loop that prevents context degradation.

🔁

Autonomous Execution Loop

Agent runs while-true: execute → test → evaluate → loop. Stops only on success, stuck state, or human interrupt.

🤝

Peer Communication

Two agents talk directly over Telegram. Shared Supabase state = shared goals. Neither agent is isolated.

🧠

Meta Loop / Context Reset

Periodic context reset prevents solution collapse (Karpathy effect). Agent stays sharp over long runs.

🚦

Backpressure + Escalation

AGENTS.md CI check prevents agents going off-rails. Failure budget (N tries = ask human) prevents infinite loops.

Meta Loop — Karpathy Effect Prevention

The Karpathy Effect: As context grows, LLMs converge toward the path-of-least-resistance in their accumulated context and stop exploring alternatives. They "collapse" into a local optimum. This gets worse past ~30K tokens. A periodic context reset breaks the collapse.

Every N iterations (or when context exceeds threshold), the Meta Loop:

  1. Compresses accumulated context into a structured summary (goal, what was tried, current state, blockers)
  2. Resets the agent with the compressed summary as fresh context
  3. Continues from the same task — but with a clean perspective

03 Two-Session Architecture

Each Ralph Loop runs as two Claude sessions — logic and execution separated by a security + sanity boundary.

  ┌─────────────────────────────────────────────────────────┐
  │                    SESSION 1: LOGIC                      │
  │              (DeepSeek R1 / Claude Opus)                 │
  │                                                          │
  │  • Holds the task spec + success criteria                │
  │  • Evaluates execution output                            │
  │  • Decides: loop / escalate / done                       │
  │  • Never touches disk or network directly                │
  └────────────────────────┬────────────────────────────────┘
                           │  structured handoff
                           ▼
  ┌─────────────────────────────────────────────────────────┐
  │                  SESSION 2: EXECUTION                    │
  │              (Claude Code / DeepSeek V3)                 │
  │                                                          │
  │  • Writes code, edits files, runs bash                   │
  │  • Runs tests, reports results back to Session 1         │
  │  • Constrained by permission_hook.py                     │
  │  • Stateless between iterations                          │
  └─────────────────────────────────────────────────────────┘
Why two sessions? The logic session maintains the spec and evaluates progress without being contaminated by execution details. The execution session can fail, get confused, or go off-track — without corrupting the goal representation held by Session 1.

Handoff Protocol

Direction Message Type Contains
S1 → S2 TASK_SPEC Goal, constraints, success criteria, failure budget remaining
S2 → S1 EXEC_RESULT What was done, test output, current state, confidence level
S1 → S2 LOOP_CONTINUE Evaluation, hint for next iteration, updated constraints
S1 → Human ESCALATE Stuck reason, what was tried, specific question for human

Sync Protocol — What Agents Say to Each Other

Every N hours, the scheduler sends a sync ping to both agents. Each agent responds with a structured status:

# SYNC MESSAGE FORMAT (agent → peer channel) AXON-ROG STATUS [2026-07-11 14:30] Current task: Implement PDF ingestion for study module Progress: kb_ingest.py refactored, 80% done Blocker: None Supabase writes since last sync: 3 (study_books, kb_chunks x2) Flagging: Nothing needs human input AXON-LEONID STATUS [2026-07-11 14:31] Current task: Ailin inference — dolphin-mistral-nemo serving Progress: Ollama running, model loaded, API tested Blocker: VRAM pressure when concurrent requests >2 Flagging: ⚠️ Need decision — queue single-file or add swap?

Escalation Filter

The peer channel is invisible to Anton by default. Agents only forward to the main chat when:

TriggerWhat Gets Sent
Genuine decision required (not just info)Specific question with context + options
Failure budget exhaustedFull debug summary + what was tried
Agents disagree on approachBoth positions + recommendation
New task needed (backlog empty)Proposed next tasks from roadmap
Key invariant: Anton only sees decisions, not process. The agents handle all back-and-forth internally. Signal-to-noise stays high.

05 Conductor Pattern — Scrum Master Node

A dedicated conductor agent acts as the scrum master of the network. It lives in a shared Telegram group alongside all worker nodes, proactively initiates communication, assigns tasks from the backlog, removes blockers, and escalates to Anton only when a real decision is needed.

Scrum master analogy: The conductor runs standups, assigns from backlog, unblocks — but doesn't do the work itself. Unlike a human scrum master, it has full read/write access to Supabase, so it maintains perfect situational awareness at all times.

Two-Layer Architecture

📡

Transport Layer (always-running)

Lightweight Python process. Sends/receives Telegram messages, routes by header, logs to Supabase. No LLM calls. Costs nothing at idle. Runs on cron or event loop.

🧠

Reasoning Layer (on-demand)

Claude Haiku / Code session, fired per-event only. Called when conductor needs to make a non-trivial decision: task conflict, stuck agent, priority change. NOT always running.

Telegram Group Communication Protocol

All nodes (conductor + workers) are members of a dedicated Telegram group. Messages carry structured headers for routing. Human can lurk silently or be excluded entirely.

Conductor Responsibilities

ResponsibilityTriggerAction
Daily standup Cron: every morning [TO:ALL] STANDUP — collect status from all nodes, log to Supabase
Task assignment Node reports idle / task completed Pull top-priority unassigned task from roadmap, set claimed_by, send [TO:NODE] TASK
Blocker resolution Node sends BLOCKER or failure budget exhausted Try to resolve via other nodes first. Escalate to Anton only if unresolvable.

Escalation Filter — What Anton Sees

The peer Telegram group is invisible to Anton by default. He only receives [TO:ANTON] messages. Everything else stays in the agent group. High signal-to-noise is a hard requirement.

06 Scheduler / Sync Cycle

The conductor's heartbeat — manages the sync cycle and task deduplication.

⏱

Sync Heartbeat

Every 2-4 hours (or event-driven on task completion): conductor sends standup ping. Each node replies with structured status JSON within 10 minutes.

📋

Goal Pull

On each sync, conductor reads Supabase personal_tasks + roadmap. Assigns highest-priority unowned task to idle nodes. Ensures alignment to current goals.

🔒

Deduplication

claimed_by + claimed_at fields in personal_tasks. Conductor sets on assignment. Nodes cannot self-assign without conductor acknowledgment.

📊

Daily Digest

Every evening: one message to Anton. Completed tasks, in-progress with ETA, blocked with reason. No noise, just the delta since yesterday.

07 Implementation Phases

1

Single-Agent Loop PLANNED

Add while-true outer loop to session_manager.py. Add success/stuck criteria to task spec. Implement failure budget (3 failures → escalate). Test on a real low-risk task (e.g. Supabase query optimization).

2

Meta Loop / Context Reset PLANNED

Add context-length monitoring. At threshold: compress to structured summary, re-init session with summary as context. Validate that task continues correctly after reset.

3

Two-Session Split PLANNED

Split logic (S1) from execution (S2). Define TASK_SPEC / EXEC_RESULT / LOOP_CONTINUE / ESCALATE message formats. Wire S1 evaluation to S2 execution via structured JSON handoff.

4

Peer Channel — Telegram Group PENDING

Create dedicated Telegram group. All nodes + conductor are members. Add peer_node.py: sends/receives messages with TO/FROM/TYPE headers, parses routing, logs to Supabase. Human optionally lurks.

5

Conductor — Transport Layer PENDING

Add conductor_node.py: lightweight always-running process. Handles: standup cron, node registration registry, routing by header, dead-node detection, daily digest to Anton. No LLM at this layer.

6

Conductor — Reasoning Layer PENDING

Add on-demand Haiku/Claude Code session called by conductor for non-trivial decisions: task conflict, stuck resolution, priority re-ranking. Add claimed_by + claimed_at to personal_tasks. Implement full task assignment cycle.

7

Backpressure + AGENTS.md PENDING

Define AGENTS.md with approved action types, forbidden patterns, escalation triggers. Add CI-style check before each execution step. Hard stop if check fails. Conductor enforces globally across all nodes.

08 Risks & Mitigations

Risk Impact Mitigation
Infinite loop — agents loop without progress Wasted tokens, blocked tasks Failure budget (N=3). Stuck detection. Meta Loop resets perspective.
Context collapse (Karpathy effect) Agent starts hallucinating / going in circles Meta Loop: compress + reset at threshold
Agents pick same task Duplicate work / conflicting writes claimed_by field in Supabase. Coordinator enforces.
Agent goes off-rails (unauthorized actions) Unintended file edits / API calls AGENTS.md CI check + permission_hook.py already in place
Peer channel noise Too many messages, escalations Escalation filter: human only sees decisions. Agents handle process.
Goal drift — agents optimize wrong metric Work doesn't match actual priorities Goals pulled from Supabase (source of truth) on every sync. Not from agent memory.

09 Open Questions for Discussion

Q1: Sync interval — 2h, 4h, or event-driven (trigger on task completion rather than time)?
Q2: What's the right failure budget N? 3 feels right for code tasks but may be too low for research tasks.
Q3: Should agents be allowed to assign tasks to each other, or only the coordinator can assign? (risk: agents game the system)
Q4: Context reset threshold — token count, iteration count, or wall-clock time?
Q5: Voice integration (GPT-4o-style) — eventual goal: agents speak to each other and to Anton via audio, not just text. What's the minimal version of this that's buildable locally?
Q6: Conductor model choice — Haiku (cheap, fast) vs Claude Code session (full tools). Is routing logic complex enough to need full tool access, or is lightweight enough for Haiku?
Q7: Can agents proactively message each other peer-to-peer (bypassing conductor), or must all communication route through the conductor? Peer-to-peer is faster but harder to audit.
Q8: Should Anton's main Telegram chat be completely separate from the agent group, or should there be a way for Anton to "drop into" the agent channel when he wants to observe?
